# Nenolink AI Marker 1.0.3 — Planning Specification

Status: planning only. Implementation is intentionally deferred.

## Product direction

Version 1.0.3 expands Nenolink AI Marker from primarily image/video marking toward a common local Windows workflow for AI transparency across visual media and office/document formats. The product remains a transparency and marking tool, not a general-purpose editor.

The release should be designed for European use: multilingual UI, multilingual disclosure labels, local processing, practical metadata, and careful language around AI transparency. The application must not claim that using AI Marker guarantees compliance with the EU AI Act or other legislation.

## Interface

Keep the existing application header and branding. Directly below the header, introduce content-type tabs:

- Images
- Video
- PDF
- PowerPoint / Slides
- Word (subject to technical feasibility)

Each tab shows only controls relevant to that content type. Common controls should behave consistently across tabs.

Normal workflows should fit within a typical laptop screen without requiring vertical scrolling. Use compact groups, progressive disclosure/advanced options, and context-sensitive controls rather than placing every parameter on screen at once.

Where technically possible, provide:
- AI badge / disclosure marking;
- optional user/company logo;
- machine-readable metadata;
- preview;
- Save As / non-destructive output;
- batch processing where it is useful and safe;
- local Windows processing.

UI language and output/label language should be separate settings. A user running the Danish UI must, for example, be able to create an English, French or other supported-language disclosure.

## Images

Retain existing image functionality and use it as the reference interaction model for other tabs where appropriate.

Keep visible AI marking, own logo, metadata, preview, local processing and batch processing. Existing image behaviour must not regress.

## Video

Retain existing video functionality where already supported. Review the UI so only video-relevant parameters are displayed.

Where technically appropriate, support visible disclosure/logo placement and relevant metadata without turning AI Marker into a video editor.

## PDF

Target:
- open PDF;
- apply disclosure to one page, selected pages, a page range, or the whole document;
- presets such as first page / all pages where useful;
- optional own logo where technically safe;
- position, size, margin and opacity where appropriate;
- metadata where robustly supported;
- preview;
- save to a new PDF and preserve the source;
- batch processing only after safe behaviour is established.

PDF implementation must account for forms, annotations, embedded fonts, signatures and other structures. Signed PDFs must not be silently modified in a way that implies the original signature remains valid.

## PowerPoint / Slides

Initial file scope: .pptx, not legacy .ppt.

Selection must be flexible. A user should be able to process:
- one slide;
- the current/chosen slide;
- multiple individually selected slides, if practical;
- a slide range;
- the whole presentation;
- useful presets such as first slide, all slides, or all except first/last.

Target features:
- AI badge/disclosure;
- optional own/company logo;
- optional short disclosure/footer text;
- placement controls;
- size, margin and opacity where appropriate;
- presentation/document metadata;
- preview or clear selection feedback;
- save to a new .pptx;
- preserve source presentation;
- batch processing of presentations only after the single-presentation workflow is robust.

The UI should make the scope of the operation unmistakable before processing, e.g. “Slide 3”, “Slides 2, 4, 7”, “Slides 3–12”, or “Entire presentation”.

## Word

Initial file scope: .docx, not legacy .doc.

Investigate before committing full implementation. Possible scope:
- whole-document disclosure;
- header/footer or another stable document area;
- optional own/company logo where technically appropriate;
- optional text disclosure;
- document metadata;
- selected sections only if this can be implemented predictably;
- save to a new .docx and preserve source formatting.

Word support may remain experimental/planned within 1.0.3 if robust modification cannot be guaranteed without damaging complex layouts.

## Logo support

Own/company logo should be available across formats wherever the underlying format makes placement safe and predictable.

Logo controls should be shared where possible:
- enable/disable;
- choose logo;
- position;
- size;
- margin;
- opacity where appropriate.

Do not force logo support into a format if it risks corrupting or materially changing the source content.

## Shared processing architecture

Avoid separate monolithic workflows for each format. Prefer a shared processing model with format-specific processors/adapters, for example:

- ImageProcessor
- VideoProcessor
- PdfProcessor
- PptxProcessor
- DocxProcessor

Shared concepts should include disclosure settings, logo settings, output naming, metadata model, language, validation, error reporting and source-file protection.

Format adapters decide which shared capabilities are supported and expose only those controls in the UI.

## Metadata

Define a common internal AI-transparency metadata model first, then map it to metadata mechanisms supported by each file format.

Potential fields include:
- AI involvement/disclosure status;
- disclosure label;
- tool/application name;
- AI Marker version;
- processing timestamp where appropriate;
- user-supplied descriptive information;
- language.

Do not imply that metadata proves how content was created. It records a disclosure/statement.

## European product direction

Design 1.0.3 for European distribution rather than treating localisation as an afterthought.

Requirements:
- preserve all existing European UI languages;
- architecture must make additional European languages easy to add;
- separate UI language from disclosure/label language;
- avoid hard-coded English strings in processors;
- Unicode-safe filenames, labels and metadata;
- terminology suitable for creators, freelancers, agencies, organisations and companies;
- local Windows processing remains a product advantage for users concerned with data control;
- documentation should distinguish transparency support from legal compliance.

Future localisation should be resource-driven so adding another language does not require changing processing logic.

## UI acceptance criteria

- Existing header remains recognisable.
- Content-type tabs are directly accessible.
- Switching tabs does not lose unrelated global settings unexpectedly.
- Each tab displays only applicable parameters.
- Primary workflow fits a normal laptop viewport without routine vertical scrolling.
- Advanced/rare settings can be collapsed.
- The selected processing scope is explicit before execution.
- Logo controls appear only where supported.
- Unsupported capabilities are not presented as working options.
- Existing image/video workflows continue to work.

## Technical acceptance criteria

- Source files are never overwritten by default.
- Output failures do not damage source files.
- Tests cover each supported selection mode.
- PPTX tests cover one slide, non-contiguous selected slides if implemented, ranges and entire presentation.
- PDF tests cover one page, selected/range pages and all pages.
- Logo and disclosure placement are tested independently and together.
- Metadata round-trip/inspection tests are added for each supported format.
- European-language strings and Unicode filenames are tested.
- Regression tests protect existing image/video behaviour.

## Implementation order proposal

1. Refactor UI shell: existing header + tabs + compact parameter panels.
2. Define shared disclosure/logo/metadata models and processor interface.
3. Move existing image/video workflows behind the shared interface without behavioural regression.
4. Implement PPTX selection and marking.
5. Implement PDF page selection and marking.
6. Evaluate/implement DOCX.
7. Complete localisation pass and European-language QA.
8. Add batch capabilities per format only after safe single-file processing.
9. Package and run full regression/release verification.

This order is a planning proposal and may change after technical spikes, especially for PDF and DOCX.
